# UX 输入对齐报告（2026-11-02）

## 1. 核对范围

本报告只比较以下四份输入，不修改其内容：

- `prd.md`
- `addendum.md`
- `DESIGN.md`
- `EXPERIENCE.md`

重点核对 2026-11-02 确认的三项规则：

1. 导师头像、昵称可编辑，保存后同步到用户视角。
2. 社群战绩与收益荣誉榜由后端分别控制。
3. 导师长固定首位；其余导师按身份上下级排序；同级采用后端顺序。

同时检查 `DESIGN.md`、`EXPERIENCE.md` 是否自行增加了未经产品输入确认的业务规则。

## 2. 总体结论

**结论：三项 2026-11-02 核心规则均已完整进入 UX，未发现核心规则缺失或反向改写；整体可判定为“核心输入已对齐，但 UX 尚有待收口项”。**

待收口项主要是：`DESIGN.md` 与 `EXPERIENCE.md` 对返回入口存在直接矛盾；UX 还自行固化了导师列表分组标题、介绍媒体顺序、保存中防重复提交等输入文档未确认的细节。这些内容不改变三项核心业务规则，但不应被当作已确认产品口径，建议删除、改为纯 Demo 表现，或显式标记 `[ASSUMPTION]` 后再确认。

## 3. 三项重点规则逐项核对

### 3.1 头像、昵称可编辑并同步用户视角

**产品输入**

- `prd.md` FR-15 明确头像支持修改、昵称使用文本输入框。
- 保存时一并保存头像、昵称和个人介绍；成功后停留当前页并提示「保存成功」。
- 用户视角的社群导师列表与导师浮层使用最新头像、昵称；导师浮层同时使用最新个人介绍。
- `addendum.md` 的 2026-11-02 规则边界再次确认头像、昵称可改，以及保存后同步到用户视角。
- 文件格式、大小、裁剪规则，以及昵称和个人介绍的校验值仍属待确认。

**UX 落位**

- `DESIGN.md` 的「个人介绍配置」包含头像更换入口、昵称输入框、只读身份、个人介绍和保存按钮；文件限制未确认时不增加错误规则。
- `EXPERIENCE.md` 的「个人介绍配置」和 UJ-5 明确头像、昵称、个人介绍可直接编辑，统一保存；保存后用户视角列表和浮层显示最新头像、昵称和个人介绍。
- `EXPERIENCE.md` 明确 Demo 不接真实上传和持久化，刷新后恢复示例数据，没有把 Demo 行为误写成正式业务持久化规则。

**判定：通过。** 可编辑字段、保存行为、用户视角同步范围和待确认边界均与产品输入一致。

### 3.2 社群战绩与收益荣誉榜后端独立控制

**产品输入**

- `prd.md` FR-12 和 `addendum.md` 明确两者是独立模块，由后端分别控制展示。
- 关闭其中一个不影响另一个；两者均关闭时不显示「社区战绩」Tab。
- 后端开启但无内容时，还要继续应用各模块自己的无数据规则。

**UX 落位**

- `DESIGN.md` 将「社群战绩」和「收益荣誉榜」画为两个独立白卡片模块。
- `EXPERIENCE.md` 在组件行为、场景切换、状态模式、交互规则及 UJ-4 中反复保持独立显隐逻辑。
- 「仅社群战绩」「仅收益荣誉榜」「两项都关闭」及无数据场景均有覆盖。

**判定：通过。** 两模块独立控制、互不影响、Tab 隐藏及无数据规则完整对齐。

### 3.3 导师长首位，其余按身份上下级，同级后端顺序

**产品输入**

- `prd.md` FR-11 明确导师长固定第一。
- 其余导师按后台配置的身份上下级优先级从高到低展示。
- 同一身份层级多人时采用后端返回顺序；前端不得硬编码创业导师、助理导师等具体身份顺序。
- `addendum.md` 明确历史画面里的创业导师、助理导师只是样例，不代表固定排序。

**UX 落位**

- `DESIGN.md` 保留导师长第一，并将具体排序行为交给 `EXPERIENCE.md`。
- `EXPERIENCE.md` 明确导师长固定第一，其余按身份上下级排序，同级采用后端返回顺序，且前端不硬编码具体身份。
- 场景「导师层级」、UJ-4 和无障碍说明均维持该顺序。

**判定：通过。** 排序权属和前端边界表达清楚，没有把历史样例误固化为业务规则。

## 4. 差距与未确认增量

### D1｜返回入口在两份 UX 中直接矛盾

- `DESIGN.md` 规定头图左上角有返回箭头，并写明 Demo 点击后仍停留社群页。
- `EXPERIENCE.md` 的出口说明却写「手机里没有返回」。
- `prd.md` 只说不规定上一级页面和返回目的地，并未确认本页是否展示返回入口。

**影响：** Demo 实现没有唯一依据，也可能让「不定义返回目的地」被误解为「必须有一个无效返回按钮」或「必须没有返回按钮」。

**建议：** 产品确认前不要将返回入口写成确定规则；两份 UX 统一为同一表述，并标明其仅为壳层导航表现或 `[ASSUMPTION]`。

### D2｜UX 自行增加导师列表的可见分组标题

- `DESIGN.md` 与 `EXPERIENCE.md` 增加「导师团负责人」「导师团成员」两个页面分组标题。
- `prd.md` 只确认导师长首位与其余导师排序，没有要求视觉上分成两组，也没有确认这两个固定文案。

**影响：** 排序规则被进一步固化为分组信息架构；如果后台身份体系变化，固定分组名称可能与真实身份标签发生语义冲突。

**建议：** 将其明确为可替换的 UX 展示方案而非业务规则，或由产品确认后补回 PRD。

### D3｜UX 自行规定介绍媒体的位置和顺序

- `DESIGN.md`、`EXPERIENCE.md` 规定图片或视频位于正文之后；`DESIGN.md` 还规定媒体按后端返回顺序排列。
- `prd.md` 只确认媒体与正文一起显示，没有确认媒体必须放在正文后，也没有定义多媒体排序字段或后端返回顺序的业务含义。

**影响：** 可能提前约束接口排序及内容编排。

**建议：** 若只是 Demo 排版，应明确为表现层样例；若要成为正式规则，应补充媒体排序、混排方式及缺失数据处理口径。

### D4｜UX 自行增加保存中不可重复提交

- `EXPERIENCE.md` 规定保存期间按钮不可重复点击。
- `prd.md` FR-15 只确认统一保存、成功提示及停留当前页，没有规定保存中状态、按钮禁用或重复请求处理。

**影响：** 这是合理的交互保护，但当前属于 UX 新增约束，不应被视作已获确认的业务验收条件。

**建议：** 可保留为通用交互默认值，但应标注为 UX 防重复提交策略，而不是产品业务规则。

### D5｜战绩行次文案存在一处内部不一致

- `prd.md`、`DESIGN.md` 及 `EXPERIENCE.md` 的组件行为都将「你的社区排行 / 本月收益」放在第二行，「团队成员收益」放在其下方。
- `EXPERIENCE.md` 的 Voice and Tone 表却写「你的社区排行」位于“战绩第三行”。

**影响：** 属于文档笔误，会使实现者对布局行次产生疑问。

**建议：** 将该处改为“战绩第二行”，与其余输入统一。

## 5. 未发现越界的部分

- UX 没有自行添加头像格式、大小、裁剪、昵称字数、个人介绍字数或必填校验。
- UX 没有把创业导师、助理导师固化成排序优先级。
- UX 没有把两个战绩模块合并成一个后端开关。
- UX 没有把收益荣誉榜误写成已排除的品牌页「月收益排行榜」。
- UX 没有把飞书昵称当成导师可编辑昵称，也没有把飞书信息带入用户视角导师卡片或浮层。
- UX 没有新增社群战绩计算周期、活跃口径或排名金额口径。

## 6. 对齐建议

1. 优先消除返回入口的 UX 内部矛盾。
2. 对导师分组标题、介绍媒体位置/顺序、保存中禁用三项，分别选择：产品确认并补入 PRD，或在 UX 中标为 `[ASSUMPTION]` / Demo 表现。
3. 修正「你的社区排行」行次笔误。
4. 三项 2026-11-02 核心规则无需重写，后续实现应继续以 `prd.md` 第 4.4 节 FR-11、FR-12 和第 4.5 节 FR-15 为验收依据。
