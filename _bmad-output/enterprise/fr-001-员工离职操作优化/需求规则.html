前端需求

企业号 · FR-001 · 员工离职操作优化
本次范围：企业主发起离职、员工确认 / 拒绝、双端消息与结果展示。

1. 页面入口与展示

  • 企业主入口：运营中心 → 员工管理 → 对应员工的「权限管理」。
  • 员工入口：员工侧「消息中心」→ 离职待确认通知。
  • 员工卡片：昵称、协作 ID、当前在职 / 离职状态；现有任务、收益、分成信息沿用原页面。
  • 消息列表：通知标题、内容摘要、通知时间、未读标记；点击查看详情后标为已读。

2. 企业主发起离职

  1. 修改权限：关闭「管理权限」后点击「确认离职并保存」。关闭开关只修改当前表单，不直接解绑。
  2. 发起确认：展示目标员工、离职影响、授权声明及协议入口。
  3. 发送条件：「具有合法操作授权」和「已阅读并同意协议」均勾选，才能点击「同意协议并发送通知」。缺任一勾选时按钮禁用。
  4. 阅读协议：打开《员工离职及企业关系解绑确认书》，返回后保留本次勾选。
  5. 发送结果：申请转为「待员工确认」，两端收到待确认消息；员工仍在职，企业关联保留。
  6. 取消结果：关闭权限表单或取消发起确认，不发送申请，不改变在职状态和企业关联。

3. 员工处理申请

  • 确认解除：先勾选「已阅读风险告知」和「自愿解除企业关联」，才能点击「确认解除关系」；缺任一勾选时按钮禁用。
  • 拒绝离职：打开拒绝确认，原因选填、最多 200 字；点击「确认拒绝」后结束本次申请。
  • 暂不处理：关闭详情、暂不处理或退出页面，都不表示同意，申请保持待确认。
  • 返回通知：拒绝确认页可返回通知详情，未提交拒绝前不改变申请结果。

4. 状态与结果对照

申请状态员工 / 关联界面与消息
未发起在职，关联保留可从权限管理发起
待员工确认在职，关联保留两端待确认通知；禁止重复发起
员工已确认已离职，关联解除两端完成通知；本次离职不可再次发起
员工已拒绝在职，关联保留两端拒绝结果；企业主可再次发起

区分两类状态：需求池「待开始」是研发进度；上表是 Demo 内离职申请的业务状态。

5. 业务边界

  • 员工确认前不解绑：企业主勾选授权或协议不能替代员工确认，不能用未读、沉默或关闭页面推定同意。
  • 历史收益继续保留：解绑不清零历史收益、不代表结算完成或责任免除；历史数据可见范围沿用来源页。
  • 旧通知不可操作新申请：历史消息仅对应其所属申请，不能用于处理另一笔申请。
  • 协议文案：沿用原需求页版本，本次适配不修改条款。

6. 待确认项

  • 请求失败后的提示文案与恢复方式。
  • 消息投递失败、重试和补发机制。
  • 申请是否支持撤回、是否超时，以及对应状态。
  • 解绑后项目权限与共享数据的完整调整清单。

上述内容尚未定稿，不作为本版已确认业务规则。Demo 使用页面内示例数据，不连接真实业务服务。

后台需求

服务端配合说明
本次无新增管理后台页面。本栏列出已知约束和待确认事项，不代替接口字段定义。

1. 申请与处理留痕

  • 来源页已要求记录：离职申请、操作人、协议版本、员工处理结果、生效时间。
  • 关联对象：申请对应目标企业及目标员工；历史消息对应其所属申请。
  • 最终结果：客户端显示的申请状态、员工状态和企业关联，以服务端处理结果为准。

2. 状态变更约束

触发结果
企业主发送申请登记为待员工确认，保留企业关联
员工确认且校验通过解除关联，记录员工处理结果与生效时间
员工拒绝结束本次申请，保留关联，记录拒绝结果
员工未处理保持待确认，不提前解绑

3. 消息要求

  • 发起后：企业主、员工均能查看待确认通知。
  • 处理后：企业主收到确认 / 拒绝结果，员工收到对应操作反馈。
  • 正式开发：来源页要求接入持久化消息、服务端状态校验和可靠投递。

4. 边界与待确认

  • 历史权益：关系解除不清除历史收益及原有结算责任。
  • 历史消息：不得通过旧通知处理新的待确认申请。
  • [待确认] 申请唯一标识、接口字段、状态枚举及返回码。
  • [待确认] 重复提交、并发处理及权限校验的具体实现。
  • [待确认] 失败提示、投递重试、补发与异常恢复。
  • [待确认] 是否新增后台查询、筛选、详情或导出能力。
