# PRD：团队项目数据分析

## 0. Document Purpose

本版最新且完整的需求真源是仓库快照 `references/team_project_member_data_mobile_h5_v4_2_with_requirements.html`，SHA-256 为 `f3ae9a24e103845c3b0acb9e959f66707cada5a4aec4d43493d1c064f467bae2`。其中内嵌的「团队项目数据 · 完整需求规则 V4.2」是明确产品规则；可见页面用于补充信息架构、字段和交互结果，但具体 Mock 数据、造数脚本、样式及代码实现不自动构成需求。

## 1. Vision

团队数据分析不再只回答“奖励来自哪里”，而要同时回答“各项目与成员带来了多少团队奖励、有效订单和出单流水”。具备权限的团队负责人可从项目、全项目成员和单项目成员三个视角比较经营表现，并沿正确入口查看既有成员详情。

项目奖励与订单经营数据使用一致的权限范围和时间窗口。跨项目汇总不重复计算订单或成员；成员关系与奖励归属保持独立，避免筛选含义混淆与奖励重复归属。

## 2. Target User

### 2.1 Jobs To Be Done

- 当查看团队经营表现时，对比项目在团队奖励与出单流水上的累计、今日和昨日表现。
- 当需要定位关键成员时，在全部项目范围按团队奖励、出单流水或有效出单量查看成员排行。
- 当分析单个项目时，在成员奖励榜与成员出单榜之间切换，并保持同一组搜索、关系与时间条件。
- 当核对成员贡献时，从不同榜单进入与其统计范围匹配的既有详情载体。
- 当接口失败、搜索或筛选无结果时，识别真实数据状态，不把异常误显示为零值。

### 2.2 Non-Users（V1）

- 不具备当前账号团队数据访问权限，或未获授权查看订单量、出单流水等敏感经营数据的用户。
- 需要编辑成员关系、奖励归属、订单、奖励或执行调账、结算、审批的运营人员；本期仅提供查看与分析。

### 2.3 Key User Journeys

- **UJ-1：小林比较项目经营表现。**
  - **Persona + context：** 小林是具备团队经营数据权限的负责人，需要判断哪些项目同时贡献了奖励和订单流水。
  - **Entry state：** 小林已进入团队数据页。
  - **Path：** 点击项目数据入口；查看累计、今日概览并切换奖励 / 流水构成；在项目排行榜切换三种出单流水降序；进入目标项目。
  - **Climax：** 小林在不改变构成图的情况下，按累计、今日或昨日出单流水找出目标项目。
  - **Resolution：** 小林可继续切换周期或排序比较项目；页面按所选条件展示对应结果。
  - **Edge case：** 接口失败时页面显示重试而不是把奖励或流水显示为 `0`。

- **UJ-2：小林定位全项目关键成员。**
  - **Persona + context：** 小林希望跨项目识别贡献成员，并避免同一成员或订单被重复统计。
  - **Entry state：** 小林位于项目数据首页。
  - **Path：** 切换到成员排行榜；选择时间、成员关系和排序维度；按用户 ID 或昵称搜索；点击成员。
  - **Climax：** 小林看到去重后的前 100 名范围，并在原有汇总抽屉中核对所选周期总计与各项目明细。
  - **Resolution：** 抽屉中的汇总与分项目明细使用成员榜当前所选周期。
  - **Edge case：** 同一成员跨项目存在关系冲突时，不由前端猜测，按 P10 决策后的服务端口径展示。

- **UJ-3：小林分析单项目双排行榜。**
  - **Persona + context：** 小林已选定一个项目，需要分别查看成员奖励和成员出单表现。
  - **Entry state：** 小林进入项目详情。
  - **Path：** 在成员奖励排行与成员出单排行之间切换；共用搜索、成员关系和五种时间条件；点击任一成员。
  - **Climax：** 奖励榜固定按团队奖励降序，出单榜固定按出单流水降序且显示有效出单量；两榜点击均打开既有「成员产生奖励详情页」并携带成员 ID、项目 ID。
  - **Resolution：** 两个榜单使用同一组搜索、关系和时间筛选语义，列表与详情的周期一致。
  - **Edge case：** 搜索或筛选无结果时显示对应空状态，成员卡片不出现备注操作。

## 3. Glossary

- **团队奖励** — 成员为当前查看团队产生的有效团队奖励，不是成员个人收入；服务带动奖励计入团队总奖励，但不得与其他奖励归属重复计入。
- **有效出单量** — 所选周期内符合有效订单口径的订单笔数；无效、撤销或不符合结算口径的订单不计入，具体状态与退款规则见 P07。
- **出单流水** — 有效订单的交易金额，单位为元，不代表成员个人收益；跨项目汇总按订单唯一 ID 去重。
- **成员关系** — 当前团队中的邀请/组织关系，用于“全部、直属、间属、直属团队、间属团队”筛选。成员加入导师团不改变原邀请关系。
- **奖励归属** — 奖励记录在发生时适用的直属、间属、服务带动等归属口径。它与成员关系是独立维度，不作为本版成员关系筛选项。
- **全项目成员** — 当前账号有权查看的全部项目范围内，按成员身份去重后的成员；其经营指标按统一周期跨项目汇总。
- **时间维度** — 累计、今日、昨日、近 7 日、近 30 日。累计指业务累计有效数据，但累计起始边界、历史迁移数据及失效数据处理仍由 P01、P08 决策；今日/昨日采用业务时区自然日，具体源时间字段、时区与 7/30 日窗口边界同样见 P01、P08。

## 4. Features

### 4.1 入口与项目总览

#### FR-1：团队数据项目入口

具备团队数据访问权限的用户可以从团队数据页「成员数据」卡片底部的内嵌项目数据入口进入项目数据首页。

**Consequences（可验收）：**

- 入口位于成员数据指标区下方、同一张成员数据卡片内部，以分隔线形成独立可点击行；不得另起“项目分析”分区或独立入口卡。
- 内嵌行展示“项目数据”、简短说明和跳转标识，整行点击后进入项目数据首页。
- 既有成员数据标题、查看详情、成员指标及底部“邀请达人加入团队”固定操作不因本入口而改变。
- 项目数据首页提供“项目排行榜”和“成员排行榜”两个 Tab。
- V4.2 未要求入口展示项目数、成员数或金额；这些 Mock 可见值不构成字段合同。

#### FR-2：项目数据概览

用户可以在项目数据首页同时查看团队奖励与出单流水的累计和今日概览。

**Consequences（可验收）：**

- 顶部概览仅提供累计、今日团队奖励，以及对应的累计、今日出单流水；不展示昨日统计。使用一个双列组件，固定流水在左、奖励在右，今日值以灰色辅助文字位于对应累计值下方，奖励值不单独高亮。
- 页头提供问号说明图标；点击打开页面统计规则说明浮层，说明内容由后台配置，字段标识为 `data.tips`。
- 累计团队奖励和累计出单流水均指当前账号有权访问项目范围内的业务累计有效数据；未定义的累计起始边界与历史迁移/失效处理分别受 P01、P08 门禁约束。
- 出单流水单位为元，含义为有效订单交易金额，不得标注或解释为个人收入。
- 今日/昨日采用业务时区自然日；奖励源时间、订单源时间、时区和日界线分别受 P01、P08 门禁约束。
- 任一概览接口异常时展示失败状态，不得把异常值显示为 `0`。

### 4.2 奖励构成与项目排行榜

#### FR-3：奖励与流水构成

用户可以按累计、今日、昨日查看项目团队奖励构成或项目出单流水构成。

**Consequences（可验收）：**

- 指标默认展示项目奖励构成，并可通过下拉切换为项目流水构成；周期默认累计，并可切换今日、昨日。
- 切换指标或周期后，按当前指标重新计算金额、排名和分组；前 5 个项目独立展示，第 6 个及之后聚合为“更多项目”。
- “更多项目”只用于图表聚合，不作为项目排行榜列表项，也不改变具体项目列表。
- 图表不随项目排行榜选择的出单流水排序而变化。

#### FR-4：项目排行榜

用户可以比较具体项目的团队奖励与出单流水，并从项目进入详情。

**Consequences（可验收）：**

- 每个项目展示项目名称、项目 Icon、累计/今日/昨日团队奖励，以及累计/今日/昨日出单流水。
- 提供且仅提供三种降序排序：累计、今日、昨日出单流水；不提供团队奖励排序。
- 切换排序只改变项目列表顺序，不改变构成图的指标、周期、排名、分组和金额。
- 项目 Icon 由后台配置；缺失时显示兜底图。
- 点击具体项目进入对应项目详情，并传递稳定的项目 ID。
- 不展示旧版“奖励成员数”字段；项目净额为零或全冲正时是否保留见 P03。

### 4.3 全项目成员排行榜

#### FR-5：全项目成员排行榜

用户可以在当前账号有权查看的全部项目范围内查看去重成员排行。

**Consequences（可验收）：**

- 每个成员项展示成员昵称、用户 ID、成员关系，以及所选周期的有效出单量、出单流水和团队奖励。
- 同一成员跨项目去重后汇总上述三项经营指标。
- 支持用户 ID 或用户昵称搜索。
- 支持五类成员关系：全部、直属、间属、直属团队、间属团队。
- 支持五种时间维度：累计、今日、昨日、近 7 日、近 30 日。
- 支持按团队奖励、出单流水、有效出单量三种指标分别降序排列，不提供升序或昵称排序。
- 最多展示前 100 名；第 100 名并列与同值稳定顺序见 P09。
- 关系筛选只使用成员关系，不使用奖励归属；跨项目关系冲突见 P10。

### 4.4 项目详情双排行榜

#### FR-6：当前项目成员双排行榜

用户可以在项目详情查看当前项目的成员奖励排行与成员出单排行。

**Consequences（可验收）：**

- 项目详情保留“成员奖励排行”“成员出单排行”两个独立 Tab，且两榜只统计当前项目。
- 两榜共用用户 ID/昵称搜索、五类成员关系和累计/今日/昨日/近 7 日/近 30 日五种时间条件。
- 两榜每个成员项均展示成员昵称、用户 ID、成员关系，以及所选周期的有效出单量、出单流水和团队奖励。
- 成员奖励排行固定按团队奖励降序，最多展示前 100 名。
- 成员出单排行固定按出单流水降序，并突出或明确展示有效出单量，最多展示前 100 名。
- 项目详情不提供排序下拉，不提供奖励升序、昵称排序或奖励归属筛选。
- 项目详情保留项目名称、导航与排行榜，不恢复旧版顶部四项 KPI 卡片。
- 两榜不展示仅来自 Mock 的 `V1/V2/V3` 标签、活跃度或加入团队日期。
- 两榜的第 100 名并列与同值稳定顺序见 P09。

### 4.5 成员点击分流

#### FR-7：按榜单入口路由成员详情

成员点击结果必须与榜单统计范围一致。

**Consequences（可验收）：**

- 从全项目成员排行榜点击成员，打开原有成员汇总详情抽屉。
- 全项目抽屉展示列表所选周期的有效出单量、出单流水、团队奖励汇总及各项目明细；抽屉周期与列表周期一致。
- 同一订单关联多个项目时，抽屉总计与分项目明细的归属及求和关系受 P13 门禁约束。
- 从单项目成员奖励排行或成员出单排行点击成员，均打开现有「成员产生奖励详情页」。
- 单项目跳转同时传递成员 ID 与当前项目 ID，不复用或新建全项目汇总抽屉。
- 成员卡片不展示备注按钮，不保留备注操作。

### 4.6 统计、去重与对账

#### FR-8：统计语义、成员关系与奖励归属

系统使用明确且互不混淆的订单、关系与奖励语义。

**Consequences（可验收）：**

- 有效出单量按所选周期统计有效订单笔数；无效、撤销或不符合结算口径的订单不计入。
- 出单流水按有效订单交易金额统计，单位为元，不得作为成员个人收入。
- 团队奖励表示成员为当前查看团队产生的有效团队奖励。
- 成员关系与奖励归属是两个独立维度；本版关系筛选不得替换为奖励归属筛选。
- 成员加入导师团后原邀请关系不变；后续适用奖励可按服务带动归属统计，且不得与其他奖励归属重复计入。
- 历史奖励保留发生时的归属口径，不因成员当前身份变化而覆盖。
- 有效订单状态、退款及部分退款规则受 P07 门禁约束。

#### FR-9：跨项目订单去重与奖励一致性

系统在跨项目汇总时避免订单与奖励被重复归属，并保持 V4.2 明确的历史奖励归属口径。

**Consequences（可验收）：**

- 跨项目汇总有效出单量和出单流水时，依据订单唯一 ID 去重，同一订单不得重复计数或计额。
- 同一订单关联多个项目时，其项目归属、分项目展示及抽屉分项目合计与去重总计的关系由 P13 决策，不在本版擅自推导。
- 服务带动奖励计入团队总奖励时，不得与其他奖励归属重复计入。
- 历史奖励保留奖励发生时适用的归属口径，不因成员当前身份或关系变化而覆盖。
- 接口失败时必须展示错误状态和重试入口，不得用 `0` 代替。
- 是否继承唯一奖励流水、原始记录不可变、独立调整/冲正记录和全链路追溯模型由 P12 决策；在决策前这些旧实现语义不是硬合同。
- 若业务确认存在退款、冲正或补发，跨日归属日期及负数/抵消展示分别受 P05、P06 门禁约束。

### 4.7 权限、状态与一致性

#### FR-10：敏感经营数据权限

只有明确授权账号可以查看订单量、出单流水等敏感经营数据。

**Consequences（可验收）：**

- 前端按授权结果控制敏感字段、榜单或入口的可见与不可用状态，最终呈现方式见 P11。
- 后端对每次查询按账号、团队和项目范围再次校验，不得仅依赖前端隐藏。
- 未授权请求不得返回有效出单量、出单流水或越权项目/成员数据。
- 团队奖励、订单指标、项目明细和成员详情采用与当前账号一致的权限范围。
- 授权角色与未授权呈现受 P11 门禁约束。

#### FR-11：页面状态与数据一致性

用户可以区分失败、无结果与真实零值，且列表与详情使用一致的所选时间条件。

**Consequences（可验收）：**

- 搜索或筛选无结果时展示语义匹配的空状态。
- 接口失败时展示错误状态和重试入口。
- 接口异常不得显示为 `0` 收益；只有服务端确认的真实零值才显示 `0` 或 `0.00`。
- 全项目成员列表与抽屉、单项目榜单与既有详情页必须使用一致的所选时间条件；近 7 日/近 30 日使用统一服务端统计窗口。

## 5. Cross-Cutting Requirements

### 5.1 数据一致性

- 概览、图表、项目榜、全项目成员榜、项目详情双榜和成员详情必须使用一致的权限范围与已定义时间语义。
- V4.2 已确认累计为业务累计有效数据、今日/昨日为业务时区自然日、近 7/30 日为统一服务端统计窗口且列表与详情一致；累计源数据起点、迁移/失效处理、源时间字段、业务时区、日界线及窗口包含边界仍由 P01、P08 决策。
- 全项目成员跨项目按成员去重；订单指标再按订单唯一 ID 去重；奖励不得重复归属且历史归属保持发生时口径。
- 项目排行与奖励构成图相互独立；两者共享底层数据但不共享展示排序。

### 5.2 安全与隐私

- 敏感经营数据必须同时经过前端可见性控制与后端账号、团队、项目范围校验。
- 用户 ID、订单指标、奖励和分项目明细只在当前账号获授权的范围内返回。
- 静态 Demo 不接真实登录、权限和生产数据，不得以 Mock 的默认可见替代正式权限合同。

### 5.3 交互与适配

- 375px 宽移动 H5 不得出现横向溢出。
- 项目 Icon 缺失或加载失败时不得破坏卡片布局和可操作性。

## 6. Non-Goals（V1）

- 不提供自定义日期；时间维度仅为累计、今日、昨日、近 7 日、近 30 日。
- 不提供成员奖励归属筛选、奖励升序、昵称排序、竞赛排名或多奖励归属标签。
- 不恢复项目详情顶部四项 KPI，不展示旧版奖励成员数字段。
- 不为单项目成员新建底部详情抽屉；单项目双榜统一跳转既有「成员产生奖励详情页」。
- 不提供成员备注操作。
- 不把“更多项目”作为项目列表项或提供二级下钻。
- 不在本 PRD 规定分页机制；“最多前 100 名”是产品上限，不等于分页合同。
- 不提供奖励、关系、订单编辑，人工调账、结算、审批或新增管理后台。
- 不连接真实接口、登录、权限或持久化到静态 Demo。

## 7. MVP Scope

### 7.1 In Scope

- 团队数据页项目入口。
- 项目数据概览中的累计/今日团队奖励与对应出单流水，以及后台 `data.tips` 配置的统计规则说明。
- 奖励 / 流水构成指标切换、累计/今日/昨日周期切换、Top 5 +“更多项目”聚合。
- 项目排行榜六个指标字段、三种出单流水降序排序、项目 Icon 配置与兜底。
- 全项目成员去重排行、三项经营指标、搜索、五类关系、五种时间、三种降序排序和前 100 名上限。
- 当前项目成员奖励榜与成员出单榜、共用筛选、固定降序和前 100 名上限。
- 全项目抽屉与单项目既有详情页的点击分流。
- 订单唯一 ID 去重、奖励不重复归属与历史归属、敏感数据权限，以及搜索/筛选空状态、错误重试和错误不显示为零。

### 7.2 Out of Scope for MVP

- §6 所列旧能力或未被 V4.2 明确要求的新增能力。
- 对既有成员汇总抽屉和「成员产生奖励详情页」进行功能重做。
- “更多项目”展开、排行上限以外的浏览机制及新增运营后台。

## 8. Success Metrics

**Primary**

- **SM-1：跨项目订单重复统计为 0。** 验收样本中，同一订单唯一 ID 在全项目有效出单量和出单流水中最多计入一次。验证 FR-5、FR-8、FR-9。
- **SM-2：奖励重复归属为 0。** 验收样本中，服务带动奖励不与其他归属重复计入，历史奖励仍使用发生时归属口径。验证 FR-8、FR-9。

**Secondary**

- **SM-3：核心需求验收通过率 100%。** FR-1～FR-11 的 Consequences 均有对应验收用例并通过。
- **SM-4：越权敏感数据返回为 0 条。** 未授权账号或越权团队/项目请求不能获得有效出单量、出单流水或受限明细。验证 FR-10。
- **SM-5：错误伪装为零的用例为 0。** 接口失败进入错误重试状态，不显示为真实 `0`。验证 FR-2、FR-9、FR-11。
- **SM-6：375px 横向溢出为 0。** 项目页、双榜、筛选区和成员详情在 375px 视口下无横向滚动。验证 §5.3。

**Counter-metrics（不得优化）**

- 不得通过改写历史奖励归属或隐藏异常提示来提高页面完整率。
- 不得通过放宽权限、前端默认展示或重复计数来增加榜单数据量。
