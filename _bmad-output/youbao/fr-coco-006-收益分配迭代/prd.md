## Vision

收益分配不再只用「主账号把收益分给子账号」这一条关系。开通权限的人可以发起协议，把收益归属方的一部分收益分给分配接收方。发起方可以是分出的那一方，也可以是收到的那一方。

用户把自己的收益分出去，和团长邀请直属 V2/V3 成员把收益分给团长，是两种协议。后台分别授权。钱的方向始终是从收益归属方到分配接收方。协议要等确认方接受后才生效。生效后，纳入协议的当日收益在次日分配完成前整笔不能提现。

## Target User

发起的人要能只看到自己有权发起的入口，并把比例和对方一次提交清楚。确认的人要在接受前知道分的是谁的收益、分给谁、分多少、哪些收益参与、何时分配、分配前哪一笔不能提现。管理员要能对同一个人分别打开或关掉两种发起资格。

**JTBD：** 配好协议发起权限之后，从对应入口提交协议；确认方从通知处理；生效后的纳入收益按次日分配结果更新双方可提现余额。

**Non-Users：** 本增量不给没有发起权限的人新的发起入口。两项发起权限也不决定谁能确认。不在这里重做历史主账号、子账号的存储。

**UJ-1：** 已开通「分配发起方个人收益」的用户打开「分配我的收益」，选择对方账号和分配比例并提交。对方从通知看到协议。接受后，分出的是发起方自己的收益，收到的是对方账号。

**UJ-2：** 同时开通两项权限的团长打开「邀请直属成员分配」，只在当前直属 V2/V3 成员里选择一人并填写比例。成员从通知看到邀请。接受后，分出的是成员的收益，收到的是团长。

**UJ-3：** 协议还在待确认时，收益归属方仍按原规则提现。生效之后，纳入协议的当日收益整笔待分配。次日分配成功，接收方拿到按比例计算的金额，归属方提现剩余金额。分配失败时两边余额都不变，重试成功后才变，且不重复入账。

## Glossary

| 词 | 含义 |
|---|---|
| 收益分配协议发起权限 | 后台「用户详情 → 收益分配」里的发起资格。由原来的「开通主账号权限」改名而来，下面有两项可独立勾选的权限。 |
| 分配发起方个人收益 | 一项发起权限。开通后，用户可发起协议，把本人收益按分配比例分给对方账号。 |
| 邀请直属 V2/V3 成员分配收益 | 一项发起权限。开通后，团长可向当前直属且等级为 V2 或 V3 的成员发起协议，成员确认后，团长按分配比例接收该成员的收益。 |
| 协议发起方 | 提交协议的账号。在「分配发起方个人收益」里同时是收益归属方。在邀请类里同时是分配接收方。 |
| 协议确认方 | 接受或拒绝协议的账号。个人分配类是对方账号。邀请类是被邀请的直属成员。 |
| 收益归属方 | 收益被拿出来分配的账号。个人分配类是协议发起方。邀请类是直属成员。 |
| 分配接收方 | 按分配比例收到金额的账号。个人分配类是对方账号。邀请类是协议发起方，即团长。 |
| 对方账号 | 协议发起方在个人分配类里选中的账号。提交后记为协议确认方，同时也是分配接收方。 |
| 分配我的收益 | 「分配发起方个人收益」的前台发起入口。 |
| 邀请直属成员分配 | 「邀请直属 V2/V3 成员分配收益」的前台发起入口。 |
| 分配比例 | 发起时填写的比例。分配金额按收益归属方纳入协议的收益乘这个比例计算。 |
| 主账号 | 历史数据里的身份。新协议页面不用它充当收益归属方的名字。历史正向协议中，原主账号映射为收益归属方。 |
| 子账号 | 历史数据里的身份。新协议页面不用它充当分配接收方的名字。历史正向协议中，原子账号映射为分配接收方。 |
| 直属成员 | 当前属于该团长直属关系的成员。邀请类的候选和提交校验都看这一关系。 |
| 团长 | 能使用邀请类入口的身份。邀请类发起时，协议发起方当前必须是团长。 |
| 待确认 | 协议已提交、确认方尚未接受或拒绝。此期间收益按原规则提现。 |
| 已生效 | 协议确认方已接受。只有这个状态的协议参与收益分配。 |
| 已拒绝 | 协议确认方已拒绝。当日收益按原规则处理。 |
| 待分配 | 两处同词。对收益：纳入协议的当日收益整笔标记，分配完成前暂不可提现。对分配记录：尚未成功入账的处理状态。 |
| 已分配 | 分配记录成功。此时更新收益归属方剩余金额和分配接收方到账金额的可提现余额。 |
| 分配失败 | 分配记录未成功。涉及的收益保持待分配，记录可重试。成功后再改为已分配。 |

## Features

### FR-1 两种协议和四个角色

一笔协议只属于一种类型，并单独记下协议发起方、协议确认方、收益归属方、分配接收方。资金从收益归属方流向分配接收方。协议发起方可以是这两方中的任意一方。

**Consequences：**

- 「分配发起方个人收益」：协议发起方是已开通该权限的用户，协议确认方和分配接收方都是对方账号，收益归属方是协议发起方。前台入口是「分配我的收益」。
- 「邀请直属 V2/V3 成员分配收益」：协议发起方是已开通该权限的团长，协议确认方和收益归属方都是被邀请的直属成员，分配接收方是该团长。前台入口是「邀请直属成员分配」。
- 新协议页面展示这四个角色，不用主账号、子账号代替它们。
- 主账号、子账号仍可识别历史数据。历史正向协议按「原主账号为收益归属方，原子账号为分配接收方」映射到新页面。

### FR-2 后台协议发起权限

管理员在「用户详情 → 收益分配」设置收益分配协议发起权限。两个选项独立勾选。

**Consequences：**

- 页面名称使用「收益分配协议发起权限」，不再以「开通主账号权限」作为这项配置的名称。
- 勾选「分配发起方个人收益」后，该用户可以发起协议，把本人收益按分配比例分给对方账号。提交时校验已开通该权限。对方账号是否可被选为分配接收方，沿用现有接收方资格。
- 勾选「邀请直属 V2/V3 成员分配收益」后，该用户可以向直属 V2/V3 成员发起协议。提交时同时校验：已开通该权限、协议发起方当前为团长、对方是其直属成员且当前等级为 V2 或 V3。
- 原来已开通主账号权限的用户，默认开通「分配发起方个人收益」。邀请权限不跟着这次迁移自动打开，由管理员单独配置。
- 确认方能否接受或拒绝，只看当前用户是不是这份协议的协议确认方。两项发起权限不参与确认校验。

### FR-3 发起、待确认、接受、拒绝

协议发起方选择协议类型、选择对方、填写分配比例并提交。确认方从通知进入详情处理。

**Consequences：**

- 发起入口按已开通的权限显示。「分配发起方个人收益」开通后显示「分配我的收益」。「邀请直属 V2/V3 成员分配收益」开通后显示「邀请直属成员分配」。当前是不是团长，不决定这个入口出不出现。一项都未开通时，不展示发起入口。两项都开通时，两个入口都展示。
- 「邀请直属成员分配」的候选列表只含当前直属的 V2/V3 成员。提交时后端按 FR-2 再校验一次。权限开着但当前不是团长，或对方不是当前直属 V2/V3 时，提交不通过。
- 某一项发起权限关闭后，该类型已经提交、仍为待确认的协议保持待确认。协议确认方仍按原确认流程接受或拒绝。关闭权限不撤回这些协议。
- 提交成功后协议为待确认，确认方能打开协议详情。待确认期间，收益按原规则提现。
- 确认前展示六项：谁的收益、分给谁、分配比例、哪些收益参与分配、什么时候分配、分配前哪笔收益暂不可提现。确认方可接受或拒绝。
- 邀请类可使用这段确认文案，其中的团长名称和分配比例取当前协议：团长 XX 邀请你将约定范围内收益的 30% 分配给 TA。接受后，纳入协议的当日收益将在分配完成前暂不可提现。系统于次日 00:00 自动分配，分配成功后，你可提现剩余金额。
- 接受时校验操作者是协议确认方，且协议仍为待确认。通过后记录确认时间和生效时间，协议变为已生效。
- 拒绝后协议为已拒绝。当日收益按原规则处理。
- 对已经不是待确认的协议再次点击接受，返回当前协议状态，不再次生效。

### FR-4 收益分配与提现

两种协议使用同一套分配规则。计算基数是收益归属方的收益。

**Consequences：**

- 协议生效前，收益按原规则入账和提现。
- 协议生效后，当日产生且纳入协议的收益，整笔标记为待分配。分配完成前，这笔金额暂不可提现。锁定的是整笔纳入金额，不是只锁分配出去的那一部分。
- 次日 00:00，系统按已生效协议的分配比例计算分配金额，向分配接收方入账。
- 分配成功后，收益归属方的剩余金额恢复可提现，分配接收方的实际到账金额进入可提现余额。
- 分配失败时，本次涉及的收益继续待分配，分配记录为分配失败并可重试。成功之前不更新双方可提现余额。
- 计算示例：收益归属方当日 100 元纳入协议，分配比例 30%。分配成功后，分配接收方到账 30 元，收益归属方剩余 70 元可提现。完成前这 100 元都暂不可提现。
- 同一团长两项权限都开通时，「分配我的收益」分出的是团长自己的收益；「邀请直属成员分配」在成员接受后分出的是成员的收益。
- 两个入口都要能验证：待确认时提现仍按原规则；分配成功后双方金额与比例一致；失败重试不会重复入账。
- 分配记录至少保留：协议、收益日期、双方账号、计算基数、分配比例、分配金额、剩余金额、处理状态、完成时间。

### FR-5 状态

协议和分配记录各自流转。收益是否参与分配，只看协议是不是已生效。

**Consequences：**

- 协议只能从待确认进入已生效或已拒绝。
- 待确认和已拒绝的协议不参与收益分配。
- 分配记录从待分配进入已分配或分配失败。
- 已分配之后更新双方可提现余额。
- 分配失败可以重试。重试成功后，该记录变为已分配，再更新双方可提现余额。

## 非目标

- 不删除、不改写历史主账号和子账号的识别方式。新页面只增加四个角色的展示，以及历史正向协议的映射。
- 不在本增量重新定义「哪些收益参与分配」。范围沿用当前收益分配功能；具体类型和字段仍见待确认。
- 不在本增量重新定义个人分配类的接收方资格。提交时沿用现有规则。
- 不把两项发起权限扩展成确认资格、提现资格或后台代用户发起。
- 不修改 FR-CoCo-003、FR-CoCo-005 以及其他已有需求的文档和页面。

## 假设与待决

- [ASSUMPTION] 邀请类协议在接受时再次校验团长身份、直属关系和成员等级，避免按过期资格变成已生效。来源将此写成建议。
- [ASSUMPTION] 关闭某一项发起权限后，立即不能再发起该类型的新协议。已生效协议继续按约定执行，终止使用独立的协议操作，不由关闭权限自动完成。来源将此写成建议。已发出且仍为待确认的协议不在这条假设里，FR-3 已定为继续由协议确认方正常接受或拒绝。
- 生效当天从何时开始纳入收益，未定。来源建议：从确认生效时刻起，只纳入之后产生的收益。例如 15:00 确认，则 15:00 前的收益沿用原规则。
- 哪些收益参与分配，原则是沿用当前收益分配功能。具体收益类型、金额字段和入账事件未在本次输入中列出。
- 同一笔收益命中多份已生效协议时如何处理，未定。来源建议：累计分配比例不超过 100%；分配到账的金额不再次参与分配；并需明确累计校验发生在发起时、确认时还是分配时。
- 团长身份取消、直属关系解除、成员等级不再是 V2 或 V3 之后：待确认协议是否失效、已生效协议从何时停止产生新的待分配、已经待分配的收益是否继续分配，均未定。
- 次日 00:00 使用的业务时区、跨日补录收益算哪一天、金额保留位数和舍入方式，未定。
- 「分配我的收益」的确认文案没有示例。FR-3 只要求两类协议都展示那六项；示例句只约束邀请类。
- 现有接收方资格的条文不在本次输入里。FR-2 只要求个人分配类沿用，不在本文件复述。
