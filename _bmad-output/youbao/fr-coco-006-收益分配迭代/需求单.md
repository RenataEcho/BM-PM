# 需求单

业务线：右豹主业务

需求名：收益分配迭代

编号：FR-CoCo-006

照着哪条现有需求做：沿用当前收益分配功能里「哪些收益参与分配」和「分配发起方个人收益」的接收方资格。历史数据仍用主账号、子账号识别。不并入其他 FR。

谁在用：

- 已开通「分配发起方个人收益」的用户，从「分配我的收益」把本人收益分给对方。
- 已开通「邀请直属 V2/V3 成员分配收益」的团长，从「邀请直属成员分配」邀请直属 V2/V3 成员把收益分给自己。
- 协议确认方，从通知进入详情，接受或拒绝。确认不依赖两项发起权限。
- 管理员，在后台「用户详情 → 收益分配」分别勾选两项协议发起权限。

从哪个入口进来：

- 前台发起：「分配我的收益」「邀请直属成员分配」。只显示已开通的入口；两项都未开通时隐藏发起入口。
- 前台确认：通知进入协议详情。
- 后台：用户详情 → 收益分配。

接着怎么点：

1. 管理员勾选协议发起权限。原来已开通主账号权限的用户，默认开通「分配发起方个人收益」。「邀请直属 V2/V3 成员分配收益」单独配置。
2. 发起方选择协议类型、选择对方账号、填写分配比例并提交。团长入口的候选列表只展示当前直属的 V2/V3 成员，提交时后端再校验。
3. 提交成功后生成待确认协议。待确认期间，收益按原规则提现。
4. 确认方看到谁的收益、分给谁、分配比例、哪些收益参与分配、什么时候分配、分配前哪笔收益暂不可提现，然后接受或拒绝。
5. 接受后协议已生效，记录确认时间和生效时间。拒绝后协议已拒绝，当日收益按原规则处理。重复点击接受时返回当前状态，不重复生效。
6. 生效后，当日纳入协议的收益整笔标记为待分配，分配完成前暂不可提现。次日 00:00 按比例把金额从收益归属方分给分配接收方。成功后归属方剩余金额恢复可提现，接收方到账金额可提现。失败则保持待分配并重试，成功后再更新双方余额。
7. 「邀请直属成员分配」只要该项权限开着就显示。当前不是团长时入口仍显示；提交时再校验团长、直属关系和 V2/V3，不符合则提交不通过。
8. 关闭某项发起权限后，该类型已经发出、仍待确认的协议不撤回。协议确认方按原流程接受或拒绝。

后台要看什么：

- 表：用户详情里的收益分配配置；每份协议；每条分配记录。
- 字段：协议发起权限的两项独立勾选。协议记录发起方、确认方、收益归属方、分配接收方。分配记录至少保留协议、收益日期、双方账号、计算基数、比例、分配金额、剩余金额、处理状态及完成时间。

哪些情况不允许：

- 未开通对应权限时，不能发起该类型协议，前台也不显示该入口。
- 邀请类提交时，发起方当前必须是团长，对方必须是其直属成员且当前等级为 V2 或 V3。
- 接受协议时，操作者必须是协议确认方，且协议仍为待确认。
- 两项发起权限不能用来判断谁可以确认。
- 待分配完成前，纳入协议的该笔收益整笔不可提现。
- 分配失败时不更新双方可提现余额。重试不得重复扣款或重复入账。
- 只有已生效的协议参与收益分配。

这次不做的：

- 不删除历史主账号、子账号数据。新页面改用四个角色；历史正向协议按「原主账号为收益归属方，原子账号为分配接收方」映射。
- 不在本增量里重写「哪些收益参与分配」和接收方资格的既有口径，只要求沿用。
- 不因关闭发起权限而自动终止已生效协议。终止走独立的协议操作。这一条在来源里写成建议，见下方待确认。

还没定的：

- 生效当天从什么时刻开始纳入收益。建议从确认生效时刻起，只纳入之后产生的收益。
- 参与分配的具体收益类型、金额字段和入账事件。原则是沿用当前收益分配功能。
- 同一笔收益命中多份协议时的累计比例上限、冲突校验时点，以及分配入账的金额能否再次参与分配。建议累计不超过 100%，到账金额不再次参与分配。
- 团长身份取消、解除直属关系、成员等级变化后，待确认协议是否失效，已生效协议何时停止产生新分配，已进入待分配的收益如何处理。
- 次日 00:00 的业务时区、跨日补录收益的归属、金额保留位数和舍入方式。
- 「分配我的收益」的确认文案没有示例。邀请类有一段示例。

2026-11-25 补充确认：

- 已开通「邀请直属 V2/V3 成员分配收益」时，邀请入口显示。当前不是团长不隐藏入口。
- 关闭发起权限后，已发出且仍待确认的协议正常接收，确认方仍可接受或拒绝。

## 来源原文

以下保持用户本次给出的原文，供 PRD 对账。

后台将「开通主账号权限」调整为 **「收益分配协议发起权限」**，支持分别开通 **「分配发起方个人收益」** 和 **「邀请直属 V2/V3 成员分配收益」**。每份协议单独记录发起方、确认方、收益归属方和分配接收方。**资金从收益归属方流向分配接收方，发起方可以是其中任意一方。**

协议类型：

| 规则项 | 分配发起方个人收益 | 邀请直属 V2/V3 成员分配收益 |
|---|---|---|
| 适用场景 | 用户主动把自己的收益分给对方 | 团长邀请直属 V2/V3 成员将收益分给自己 |
| 协议发起方 | 已开通该权限的用户 | 已开通该权限的团长 |
| 协议确认方 | 对方账号 | 被邀请的直属成员 |
| 收益归属方（谁分出） | 发起方 | 直属成员 |
| 分配接收方（谁收到） | 对方账号 | 发起方，即团长 |
| 前台发起入口 | 分配我的收益 | 邀请直属成员分配 |

「主账号 / 子账号」可继续用于识别历史数据。新协议页面统一展示协议发起方、协议确认方、收益归属方、分配接收方。历史正向协议可按「原主账号为收益归属方，原子账号为分配接收方」映射。

后台在「用户详情 → 收益分配」设置协议发起权限，两个权限可独立勾选。

| 权限选项 | 开通后的能力 | 发起时的后端校验 |
|---|---|---|
| 分配发起方个人收益 | 发起协议，将本人的收益按约定比例分给对方 | 已开通该权限，接收方资格沿用现有规则 |
| 邀请直属 V2/V3 成员分配收益 | 向直属 V2/V3 成员发起协议，成员确认后按约定比例接收收益 | 已开通该权限、发起方当前为团长、对方是其直属成员且当前等级为 V2 或 V3 |

原权限迁移：原来已开通主账号权限的用户，默认开通「分配发起方个人收益」。邀请权限由管理员单独配置。团长同时拥有两项权限时，前台显示两个发起入口。用户只看到具备资格的发起入口。两项均未开通时，隐藏发起入口。收到协议的用户可从通知进入详情并处理协议。接受权限取决于当前用户是否为协议确认方。关闭权限的建议：关闭后立即禁止发起该类型的新协议。已生效协议按约定继续执行，终止通过独立的协议操作处理。待确认协议的处理见待确认项。

发起：选择协议类型、对方账号、分配比例并提交。团长入口候选只含当前直属 V2/V3，提交时再校验。待确认期间收益可按原规则提现。确认前告知谁的收益、分给谁、分配比例、哪些收益参与分配、什么时候分配、分配前哪笔收益暂不可提现。接受时校验操作者是协议确认方且协议仍待确认，记录确认时间和生效时间。建议邀请类在接受时再次校验团长身份、直属关系和成员等级。拒绝后为已拒绝，当日收益按原规则处理。重复接受返回当前状态。

团长邀请确认文案示例：团长 XX 邀请你将约定范围内收益的 30% 分配给 TA。接受后，纳入协议的当日收益将在分配完成前暂不可提现。系统于次日 00:00 自动分配，分配成功后，你可提现剩余金额。

两类协议同一套分配规则，以收益归属方的收益为计算基数。生效前按原规则入账和提现。生效后当日纳入协议的收益整笔待分配，完成前暂不可提现。次日 00:00 按有效协议比例计算并向接收方入账。成功后归属方剩余金额恢复可提现，接收方实际到账金额进入可提现余额。失败则继续待分配并重试，成功后再更新双方可提现余额。

计算示例：直属成员当日 100 元参与分配，比例 30%。次日成功后团长到账 30 元，成员剩余 70 元可提现。完成前这 100 元均暂不可提现。

实现建议：扣减分配金额、接收方入账、释放收益归属方剩余金额作为一次一致的账务处理。重试使用同一分配单号。分配记录至少保留协议、收益日期、双方账号、计算基数、比例、分配金额、剩余金额、处理状态及完成时间。

状态：协议为待确认 → 已生效 / 已拒绝，只有已生效参与分配。分配记录为待分配 → 已分配 / 分配失败。已分配后更新双方可提现余额。失败可重试，成功后更新为已分配。

验收重点：同一个团长同时开通两项权限时，从「分配我的收益」发起，应分出团长自己的收益。从「邀请直属成员分配」发起，应由成员确认并分出成员的收益。两个场景都要验证待确认时提现正常、分配成功后双方金额正确、失败重试无重复入账。
