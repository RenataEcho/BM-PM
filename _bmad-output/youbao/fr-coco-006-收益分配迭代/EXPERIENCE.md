# FR-CoCo-006 收益分配迭代 — Experience Spine

视觉以 `DESIGN.md` 为准。现有画面 `imports/youbao-revenue-distribution-demo.html` 提供分区和已有动作。与两份文档冲突时，以 `DESIGN.md` 和本文件为准。

## Foundation

两块产品表面：C 端手机、管理后台里的用户详情。手机是主路径。后台只改「用户详情 → 收益分配」这一区。

手机视觉继承 `docs/design/移动端设计规范.md`。后台视觉继承 `docs/design/admin-ui-spec.md`。放到迭代记录台时，外壳继承 `docs/design/iteration-shell/DESIGN.md`，场景切换留在手机外面。本文件只写这一刀的行为差。

词和 PRD 用语保持一致：协议发起方、协议确认方、收益归属方、分配接收方、分配我的收益、邀请直属成员分配、待确认、已生效、已拒绝、待分配、已分配、分配失败。

## Information Architecture

| Surface | Reached from | Purpose |
|---|---|---|
| 分配记录 | 打开收益分配，默认页签 | 看与自己有关的分配结果 |
| 分配用户 | 分段页签 | 看协议，并从已开通的入口发起 |
| 发起表单 | 对应发起入口，或已结束协议上的再次发起 | 选择对方并填写分配比例 |
| 协议详情 | 协议卡、记录详情里的查看协议、通知 | 核对四个角色；待确认时接受或拒绝 |
| 分配记录详情 | 分配记录条 | 看单次分配的基数、比例、金额和状态 |
| 规则说明 | 页头规则按钮 | 看已定的生效和提现口径 |
| 解除确认 | 已生效协议上的解除协议 | 确认不再按这份协议分配新收益 |
| 用户详情 · 收益分配 | 后台用户详情 | 配置两项发起权限，查看该用户相关协议和分配记录 |

通知只打开对应的协议详情。通知中心本身不在这一刀里重做。

分配记录页签不放发起入口。发起入口只在分配用户页签、筛选的上方。一项权限一行。未开通的不渲染。

→ 现有分区：`imports/youbao-revenue-distribution-demo.html`。本文件把页头上的「发起协议」改成页内两行入口，把手机内的演示账号条移出产品画面。

## Voice and Tone

短句，把人和钱分开说。品牌语气在 `DESIGN.md` 的 Brand & Style。

| Do | Don't |
|---|---|
| 「我发起的」「我收到的」 | 把这两句当成资金方向 |
| 「我分出 30%」「我接收 30%」 | 「主账号分给子账号」 |
| 「协议已发送」「协议已生效」「已拒绝协议」「协议已解除」 | 「操作成功」 |
| 「当前没有可邀请的直属 V2/V3 成员。」 | 隐藏邀请入口来代替这句 |
| 「当前不是团长，不能发起。」 | 在入口上提前解释团长规则 |
| 未定处写 `[待确认]` | 把建议口径写成已经生效的规则 |

邀请类确认句用 PRD 原文，只替换团长名称和比例。个人分配类确认不另写一段话，用确认六项的六行标签。

## Component Patterns

行为。外观在 `DESIGN.md` 的 Components。

| Component | Use | Behavioral rules |
|---|---|---|
| 页头 | 两个页签共用 | 标题固定。规则按钮始终可点。 |
| 规则按钮 | 页头 | 打开规则说明。 |
| 发起入口 | 分配用户 | 按权限渲染。「分配我的收益」进入个人分配表单。「邀请直属成员分配」进入邀请表单。当前是不是团长，不改变邀请入口是否出现。 |
| 分段页签 | 收益分配 | 切换时保留各自的筛选。默认页签是分配记录。 |
| 协议筛选 | 分配用户 | 全部协议、我发起的、我收到的。筛选的是协议发起方，不是收益归属方。 |
| 协议卡 | 分配用户 | 只显示当前用户是协议发起方或协议确认方的协议。待你确认的排在前面，其余按发起时间新的在前。点卡片打开协议详情。底部按钮不重复触发卡片点击。 |
| 状态标签 | 协议卡、协议详情 | 确认方看到待确认时写「待你确认」。发起方看到同一状态时写「待对方确认」。已生效、已拒绝、已解除用状态原名。 |
| 分配记录条 | 分配记录 | 只显示当前用户能看到其协议的记录。点按打开分配记录详情。 |
| 记录筛选 | 分配记录 | 方向和时间同时生效。零金额默认不在主列表，底部开关可展开。 |
| 协议详情 | 浮层 | 四个角色始终用词表里的名字。待你确认时，接受和拒绝之前先展示确认六项。 |
| 确认六项 | 协议详情 | 六行都在。值取当前协议。参与收益的具体类型未定，行内保留 `[待确认]`。 |
| 发起表单 | 浮层 | 个人分配的候选沿用现有接收方资格，本增量不重写资格条文。邀请的候选只含当前直属且等级为 V2 或 V3 的成员。提交时再校验一次权限和资格。 |
| 解除确认 | 轻提示 | 沿用现有 Demo：能看到该协议、且协议已生效的一方可以打开。确认后状态变为已解除，并记下解绑时间。本增量不改谁可以解除。 |
| 规则说明 | 浮层 | 只讲已定口径。累计比例、到账金额能否再次参与分配，留在 `[待确认]`，不放进已定段落。 |
| 分配记录详情 | 浮层 | 展示计算基数、分配金额、剩余金额、处理状态。分配失败时写明双方可提现余额未更新。可以转到协议详情。 |
| 权限勾选 | 用户详情 · 收益分配 | 两项独立保存。关掉某一项后，不能再发起该类型的新协议。已经发出且仍待确认的协议不撤回，确认方仍可接受或拒绝。 |
| 后台协议表 | 同一区块 | 只读展示四个角色和状态。不在表内代用户发起、接受或拒绝。 |
| 后台分配记录表 | 同一区块 | 只读。失败行不写完成时间。重试不在这张表上提供按钮。 |

`[ASSUMPTION]` 关闭发起权限后，已生效协议继续执行。终止只走解除确认，不由取消勾选自动完成。这是来源里的建议，页面上取消勾选不出现解除文案。

`[ASSUMPTION]` 重试由系统按同一笔分配执行。前台和后台表都不提供重试按钮，也不展示分配单号。

## State Patterns

| State | Surface | Treatment |
|---|---|---|
| 默认打开 | 分配记录 | 展示非零记录。无记录时写「暂无符合条件的记录」。 |
| 无协议 | 分配用户 | 「暂无符合条件的协议」。发起入口仍按权限显示。 |
| 无发起权限 | 分配用户 | 不渲染发起入口。已有协议和记录仍按是否相关显示。 |
| 只有一项权限 | 分配用户 | 只渲染对应的一行入口，点按直接进入该表单。 |
| 两项权限 | 分配用户 | 两行都在。个人分配分出的是发起方自己的收益。邀请在对方接受后分出的是成员的收益。 |
| 邀请候选为空 | 发起表单 | 选择框下写「当前没有可邀请的直属 V2/V3 成员。」发送仍提交，由校验返回结果。 |
| 提交校验失败 | 发起表单 | 表单保持打开。按失败原因显示一句：「未开通该发起权限。」「当前不是团长，不能发起。」「对方不是当前直属 V2/V3 成员。」「请填写 0.01 到 100 的分配比例。」 |
| 待确认 | 协议详情 | 收益按原规则提现。确认方看到拒绝和接受协议。发起方看到待对方确认，没有接受按钮。 |
| 已生效 | 协议卡、协议详情 | 纳入协议的当日收益整笔待分配，分配完成前暂不可提现。锁定整笔纳入金额。 |
| 已拒绝 | 协议详情 | 当日收益按原规则处理。再次接受不会把它变成已生效。 |
| 重复接受 | 协议详情 | 协议已经不是待确认时，刷新为当前状态，不第二次写入生效时间。提示用当前状态名。 |
| 已分配 | 分配记录详情 | 分配接收方增加分配金额，收益归属方的剩余金额恢复可提现。 |
| 分配失败 | 分配记录条、详情 | 状态为分配失败。双方可提现余额不变。记录留在列表里，成功前不改成已分配。 |
| 零金额 | 分配记录 | 默认折叠。开关文案是「查看零金额记录（N）」和「收起零金额记录（N）」。 |
| 权限刚关闭 | 后台与手机 | 新发起入口立即按新权限消失。该类型仍待确认的协议留在确认方的列表里，接受和拒绝仍可用。 |
| 空筛选 | 两个列表 | 沿用「暂无符合条件的协议」或「暂无符合条件的记录」。 |

## Interaction Primitives

- 点按完成打开、切换、提交、接受、拒绝、解除。
- 协议卡底部按钮和卡片主体分开响应。
- 底部浮层：点遮罩或关闭按钮关闭。解除确认只由取消或确认解除关闭。
- 发送成功后关闭表单，协议筛选切到「我发起的」，提示「协议已发送」。
- 接受成功后留在协议详情，状态改为已生效，提示「协议已生效」。拒绝后提示「已拒绝协议」。解除后提示「协议已解除」。
- 提示约 2.4 秒后消失。
- 后台保存只提交两项复选框。保存成功用后台 Toast，文案「已保存发起权限」。
- 不在这一刀里做下拉刷新、滑动删除和批量操作。

## Accessibility Floor

对比和颜色分工在 `DESIGN.md`。行为上：

- 资金方向同时有文字和正负号。已生效不靠绿色传达。
- 页签写出当前项。筛选写出是否按下。规则按钮和关闭按钮有可读名称。
- 发起入口、接受协议、确认解除的可点高度不小于 44px。
- 打开浮层时，焦点进入标题之后的第一项操作。关闭后回到触发它的按钮。
- 减少动态效果时，浮层直接出现，不播放上滑。
- 状态变化除了改文字，还用提示再报一次。

## Responsive & Platform

手机按 `{spacing.phone}` 单列。发起入口是整行，不挤进页头。

管理后台是桌面用户详情里的一个区块。两项权限用复选框，表用管理后台表格。字段不超过这一区块的三块，不因为协议字段多就新开详情路由。

迭代记录台同时放这两块：前端交互页签里是手机和场景条，管理后台页签里是用户详情的收益分配区。场景条至少能切到林川、阿禾、Renata🦋1、小满。场景条不是产品界面。

## Inspiration & Anti-patterns

- **沿用现有 Demo：** 分配记录和分配用户两个页签、协议卡上的对方与累计、记录的方向筛选、零金额折叠、四个角色出现在详情里、解除后保留历史记录。
- **改掉的 Demo 习惯：** 页头单一「发起协议」、手机框底的演示账号、宋体、收入绿色和支出褐红。入口改成两个原名，账号切换留在记录台场景条。
- **不提前做成交互的建议：** 接受时再次校验团长和直属关系、累计分配比例不超过 100%、生效时刻之前的收益不纳入、资格变化后自动失效。这些仍是 PRD 的待确认项。

## 未定口径

下面这些在页面上以 `[待确认]` 出现，或根本不做成一种已定状态。

- 生效当天从哪个时刻开始纳入收益。
- 参与分配的具体收益类型、金额字段和入账事件。原则只写「沿用当前收益分配」。
- 同一笔收益命中多份已生效协议时，累计比例在何时校验，以及已经到账的金额能否再次参与分配。
- 团长身份取消、直属关系解除、成员不再是 V2 或 V3 之后，待确认协议是否失效，已生效协议何时停止产生新的待分配，已经待分配的收益是否继续分配。
- 次日 00:00 的业务时区、跨日补录算哪一天、金额保留位数和舍入方式。
- 个人分配类没有确认例句。确认六项的六行就是该类型的确认内容。
- 个人分配的接收方资格条文不在本增量里重写。表单候选只要求沿用现有规则。

## Key Flows

人物用现有 Demo 里的账号：林川是开通两项权限的团长，阿禾只有「分配发起方个人收益」，Renata🦋1 是林川的直属 V2 成员、自己也有个人分配权限，小满是林川的直属 V3 成员、没有发起权限。

### Flow 1 — UJ-1 阿禾把自己的收益分给小满

1. 阿禾打开收益分配，停在分配记录。
2. 她切到分配用户，只看到「分配我的收益」。
3. 她点该入口，选择小满，填写分配比例，发送。
4. 列表出现待对方确认的协议。筛选落在我发起的。
5. 小满从通知打开协议详情，先看到确认六项：收益是阿禾的，分给小满，比例是刚填写的值，参与收益标着沿用和 `[待确认]`，分配时间是次日 00:00，分配前整笔纳入收益暂不可提现。
6. **Climax：** 小满点接受协议。详情变为已生效。阿禾的卡是「我发起的」和「我分出」。小满的卡是「我收到的」和「我接收」。

失败：阿禾未开通该权限时，入口不出现，表单也不能提交。小满在协议已不是待确认时再点接受，详情停在当前状态，生效时间不改写。

### Flow 2 — UJ-2 林川邀请 Renata🦋1 把收益分给自己

1. 林川打开分配用户，看到「分配我的收益」和「邀请直属成员分配」两行。
2. 他点「邀请直属成员分配」。候选里有 Renata🦋1 和小满，没有非直属、也没有 V2/V3 以外的人。
3. 他选择 Renata🦋1，填写 30%，发送。
4. Renata🦋1 从通知打开详情。六项之上有邀请句：「团长 林川 邀请你将约定范围内收益的 30% 分配给 TA。……」
5. 她核对：收益归属方是自己，分配接收方是林川，协议发起方是林川，协议确认方是自己。
6. **Climax：** 她接受。林川的卡写「我发起的」和「我接收 30%」。Renata🦋1 的卡写「我收到的」和「我分出 30%」。分出的是她的收益。

失败：林川当前不是团长时，邀请入口仍在。候选可以为空。发送后提示「当前不是团长，不能发起。」对方不是当前直属 V2/V3 时，提示「对方不是当前直属 V2/V3 成员。」协议保持未创建。

### Flow 3 — UJ-3 Renata🦋1 等到次日分配

1. 协议还在待确认时，Renata🦋1 按原来的方式提现。
2. 她接受之后，当天纳入协议的收益整笔变为待分配，这笔在分配完成前不能提现。
3. 次日 00:00，系统按 30% 计算。她当天纳入 100 元时，林川到账 30 元，她剩余 70 元。
4. **Climax：** 分配记录变为已分配。Renata🦋1 看到「分给 林川」、减号和 30 元。林川看到「来自 Renata🦋1」、加号和 30 元。她的剩余 70 元恢复可提现，他的 30 元进入可提现余额。

失败：分配记录变为分配失败，金额不带正负号，详情写双方可提现余额未更新。系统稍后重试同一笔。成功前两个人的可提现余额都不变，成功后只入账一次。

### Flow 4 — 管理员分别打开林川的两项权限

1. 管理员打开林川的用户详情，进入收益分配。
2. 「分配发起方个人收益」已经勾选，因为原来的主账号权限迁到了这一项。「邀请直属 V2/V3 成员分配收益」未勾选。
3. 管理员勾上第二项并保存。
4. **Climax：** 林川再打开分配用户时，两行入口都在。他从「分配我的收益」分出的仍是自己的收益。

失败：管理员后来取消某一项。林川不能再发起该类型的新协议。已经发给 Renata🦋1、且仍待确认的那份不消失，她仍能接受或拒绝。取消勾选的保存结果里不包含解除。
